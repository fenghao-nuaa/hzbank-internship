# SemanticaAdapter README 重构设计

## 目标

重写项目 README，使读者首先理解公司 Agent 当前存在的问题、为什么需要引入 Semantica，以及 Semantica 的哪些能力能够解决这些问题；接口和可替换后端属于技术实现方式，不再作为开篇重点。

## 目标读者

- 希望理解项目价值的导师、项目负责人和业务人员；
- 需要评估 Agent 审计、审批与可追溯能力的银行合规人员；
- 负责接入或继续开发本项目的工程人员。

## 核心叙事

开篇围绕以下问题展开：

1. Agent 通常可以给出审核结果，但事后难以回答使用了哪些规则和证据；
2. Agent 规则、法规版本和审核逻辑没有与 Agent 画像稳定绑定；
3. 推理结论、人工审批、政策例外和证据来源分散，难以形成完整审计链路；
4. 银行场景需要决策可解释、可追溯、可人工复核和可供监管检查。

随后说明引入 Semantica 的原因：使用 Context Graph 固化决策上下文，通过确定性推理记录规则命中，通过 Provenance 保存来源链，通过 Ontology 约束输入语义，并通过 JSON、RDF 和 PROV-O 形成可导出的审计材料。

## README 结构

1. **项目介绍**：问题、引入 Semantica 的目的和项目能够形成的治理闭环。
2. **需要 Semantica 解决什么问题**：从规则绑定、审核依据、人工复核、审计检查四个方面说明。
3. **整体工作流程**：展示 Agent 请求、画像、证据、本体、规则推理、决策、审批和导出的完整链路。
4. **已集成的 Semantica 模块**：详细说明 `context`、`reasoning`、`provenance`、`ontology` 和 `export` 的实际用途与实现状态。
5. **尚未直接集成的模块**：说明 `kg`、`ingest`、`semantic_extract` 等属于后续范围，避免误导。
6. **当前实现能力**：介绍失败关闭、审计隔离、审批例外和离线完整性验证。
7. **金额核对案例**：以凭证金额和总账金额不一致为例，说明 Agent 规则如何固化、依据如何查询以及人工如何审批。
8. **快速开始**：安装、运行示例和离线验证。
9. **项目结构与扩展方式**：面向开发人员说明主要目录和后端隔离边界，但不抢占项目价值叙事。
10. **测试和生产边界**：列出当前测试情况，以及银行上线前仍需接入的企业控制。

## 表述原则

- 先讲业务问题和项目价值，再讲接口与架构；
- 不把 SemanticaAdapter 描述成 Semantica 的完整复制品；
- 不宣称已经集成尚未封装的 `semantica.kg`、采集、语义抽取或可视化能力；
- 区分“可运行原型”和“银行生产合规系统”；
- 区分系统级可解释依据与模型私有思维过程；
- 对 Semantica 0.6.6 的审批兼容分支和共置哈希清单的信任边界保持透明。

## 验收标准

- 第一段能够直接回答“为什么引入 Semantica”；
- README 单独列出已集成模块及其用途；
- 金额核对案例能够说明规则、证据、推理、决策和审批如何形成审计链；
- 安装和示例命令与当前源码一致；
- 不与 `docs/capability-matrix.md` 和当前 0.6.6 实现状态矛盾；
- 不出现 `TBD`、`TODO` 或未经实现验证的能力声明。
